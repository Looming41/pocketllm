# Meta 기술 활용 설계

## 0. 문제: 보안 기관은 왜 Claude나 ChatGPT를 못 쓰나
군, 공공, 방산, 금융처럼 내부 정보가 밖으로 나가면 안 되는 조직은 인터넷 LLM에 프롬프트를 보내는 순간 유출로 간주합니다. 그래서 필요한 것은 두 가지입니다.
1. **현장(폐쇄망)에서는 네트워크가 0**이어야 합니다. 모델, 런타임, 정책이 모두 드라이브 안에 있어야 합니다.
2. 그래도 **어떤 모델을, 어떤 양자화로, 어떤 기기에** 넣을지 정하는 일은 전문가와 클라우드급 지능이 있으면 훨씬 쉽습니다.

→ PocketLLM은 Meta 기술을 **두 구역으로 나누어** 씁니다. 이 경계가 제품 설계의 중심입니다.

```
┌───────────────────── 준비 구역 (인터넷 O, 비기밀) ─────────────────────┐        ┌──────────── 현장 (폐쇄망, 인터넷 X) ────────────┐
│ Meta Model API · Muse Spark                                             │        │ Meta 오픈 웨이트 모델 (로컬 실행)               │
│  ① fleet-plan : 임무 목표 + 대상 노트북 사양 → 드라이브 구성 제안       │  USB   │  · Llama 4 Scout (109B MoE) ← 전문가 스트리밍   │
│  ② evalset    : 도메인 합성 평가 문항 생성(실명·기밀 없음)              │ ─────▶ │  · Muse Glimmer 30B (Apache 2.0)               │
│  ③ qualify    : 후보 양자화별 답변 채점(LLM-as-judge) → 최소 합격 모델  │ 서명된 │  · Llama 3.x 8B/3B (저사양 기기)               │
│  ④ seal       : 매니페스트 해시 + 조직 키로 서명                         │ 드라이브│  · (선택) Llama Guard: 로컬 정책 필터          │
│ ※ 로컬 플래너가 모든 제안을 실제 측정값으로 검증 (클라우드는 제안만)     │        │ 무결성 검증 · 네트워크 0 · 메타데이터 감사 로그 │
└─────────────────────────────────────────────────────────────────────────┘        └─────────────────────────────────────────────────┘
```

## 1. 준비 구역: Meta Model API(Muse Spark)가 하는 일 (구현됨)
| 명령 | 입력 | Muse Spark의 역할 | 로컬 검증 |
|---|---|---|---|
| `pocketllm fleet-plan --profiles dir/ --goal "..."` | 대상 노트북들에서 오프라인으로 수집한 `profile.json`, 임무 목표 문장 | 목표를 제약(우선순위, 컨텍스트, 오프라인 여부)으로 해석하고, IT 담당자용 배포 브리프 작성 | 플래너가 기기마다 판정을 계산하고 **가장 약한 기기에서도 도는 모델 목록**을 산출 |
| `pocketllm evalset --domain "정비 매뉴얼 Q&A" -n 30` | 도메인 설명 | 합성·비기밀 평가 문항과 모범 답안 생성 | 운영자가 검토 후 사용 |
| `pocketllm qualify --evalset ... --candidates q2=url q3=url q4=url` | 후보 양자화 모델들의 로컬 답변 | **채점관**(1~5점 + 이유) | 작은 모델부터 평가해 **합격선을 넘는 가장 작은 양자화**를 선택(메모리와 발열 최소화) |

- 코드에서 강제하는 것(`provision.py`): 드라이브 정책이 `airgap`이면 이 기능들은 **실행을 거부**합니다. 현장 데이터는 업로드 경로 자체가 없습니다.
- 클라우드 판단은 "제안"일 뿐입니다. 값은 범위 안으로 잘리고(`assistant.validate`), 모델 선택은 로컬 플래너와 실측이 결정합니다.
- 폐쇄망 안에서 재검증이 필요하면 `qualify --local-judge <로컬 모델 URL>`로 클라우드 없이 채점할 수 있습니다.

## 2. 현장: Meta 오픈 웨이트 모델
| 모델 | 이유 | 상태 |
|---|---|---|
| **Llama 4 Scout 17B-16E (109B MoE)** | 100B급 목표 모델. 토큰당 활성 17B, 전문가 16개 → **전문가 스트리밍 엔진의 주 대상** | llama.cpp `llama4` 아키텍처 지원 ✅. 노트북 실측은 TODO |
| **Muse Glimmer 30B** | Apache 2.0이라 **기관 재배포와 사전 탑재에 법적으로 가장 유리**. 4-bit에서 20GB 미만 🔎 | llama.cpp `muse-glimmer` 아키텍처 ✅. GGUF 확인 필요 |
| Llama 3.1 8B / 3.2 3B | 16GB 이하, 팬리스 기기의 기본값 | ✅ |
| Llama Guard (3 1B/8B, 4 12B) | 조직 정책 카테고리(예: "기밀 표식이 붙은 내용의 재생산")로 프롬프트와 응답을 로컬에서 분류 | 설계 단계. Guard 4의 GGUF·llama.cpp 지원은 미확인 |

## 3. 해커톤 심사 관점에서의 "Meta 활용" 요약
- Muse Spark는 **장식이 아니라 공급 과정(provisioning)의 핵심 단계 세 곳**(계획, 평가셋, 채점)에 들어갑니다.
- Meta 오픈 웨이트는 **실제 추론 대상**입니다. 특히 Llama 4 Scout의 MoE 구조가 PocketLLM 엔진과 기술적으로 맞물립니다.
- 두 구역 분리는 "보안 기관도 Meta AI의 혜택을 받는 방법"이라는 임팩트 서사가 됩니다.

## 4. 미구현과 확인할 것
- 실제 API 키로 호출해 보기(지금은 모의 서버 테스트만 했습니다). 모델 ID는 `/v1/models`로 확인
- 한국에서의 Muse Spark API 접근 가능 여부
- 해커톤 규정상 "Meta 기술 사용"의 인정 범위(오픈 웨이트 로컬 실행 포함 여부)

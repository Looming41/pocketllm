## 3. 데모 대본 (2~3분 권장. 공식 길이 제한 확인)
1. (0:00) 문제 제기: "100B 모델을 내 노트북에서? 다운로드에 1시간 걸리고, 그다음에야 안 된다는 걸 알게 됩니다."
2. (0:15) USB를 꽂고 런처를 실행합니다. UI가 하드웨어를 탐지하고 드라이브 배지가 `USB`로 표시됩니다.
3. (0:35) 판정표: Scout 109B는 "impractical, 53GB를 드라이브에서 페이징, ≤0.2 tok/s", 8B는 "runs". **정직한 이유**를 함께 보여 줍니다.
4. (0:55) Meta 도우미에 "오프라인으로, 실시간 대화 가능한 가장 큰 모델"을 입력합니다. Muse Spark가 제약 조건을 만들고, 로컬 플래너가 검증한 결과가 나옵니다(클라우드 라벨 표시).
5. (1:20) 로컬 모델을 로드하고 채팅합니다. TTFT, tok/s, RAM이 실시간으로 표시됩니다.
6. (1:45) 자동 튜닝을 실행해 기본 설정과 튜닝 설정을 실측으로 비교합니다.
7. (2:05) Wi-Fi를 끕니다. 배지가 `offline`으로 바뀌고 채팅은 계속됩니다.
8. (2:20) (메모리가 되면) Scout 실행 화면, 또는 페이징 실측 결과 그래프를 보여 줍니다.
9. (2:35) 로드맵: 같은 소프트웨어가 장치 메모리를 가진 USB 컴퓨트 모듈을 백엔드로 쓰는 하이브리드 구조.

화면에 항상 표시할 문구: "Inference runs on this computer's CPU/GPU. The drive stores software and models."

## 5. 심사 기준 대응 (비중은 미검증)
- **Impact**: "다운로드 전에 정직한 판정"으로 비전문가의 실패 비용(시간, 디스크, 실망)을 없앱니다. 오프라인과 개인정보 보호도 해당합니다.
- **Meta 기술 활용**: Muse Spark는 실행 제약 해석에, Meta 오픈 웨이트는 실제 로컬 추론에 씁니다. 장식이 아니라 핵심 흐름에 들어 있습니다.
- **기술 깊이**: GGUF 텐서 단위 메모리 회계, MoE 전문가 단위 배치(`-ncmoe`), 대역폭 기반 속도 상한, 잡음을 고려한 실측 튜닝, 통합 메모리 회계, 버전 고정 런타임
- **데모**: USB 연결 → 판정 → 채팅 → 튜닝 → 오프라인 전환의 연속 흐름
